Fix 1: Companion Worker Lifecycle Race (Priority 0)
--------------------------------------------------------------------------------

Root cause:
  _ensure_worker() in ui/companion_state.py had multiple synchronization defects:
  (1) worker.start() was called OUTSIDE the lock, allowing two concurrent callers
      to both create and start two workers simultaneously;
  (2) _stopping.clear() inside _ensure_worker could reverse an intentional shutdown;
  (3) _ensure_worker relied solely on threading.is_alive() for health checks, but
      a thread can report alive while unwinding from a BaseException;
  (4) A dying worker could strand queued work with _inflight never returning to zero;
  (5) Shutdown could be undone by an ordinary concurrent submission.

  The race manifested as: under load, _wait_settled() would time out with
  "inflight was never released" because a newly-submitted task had no live worker
  to process it.

Files changed: ui/companion_state.py

Summary of changes:
  1. Added self._worker_gone flag to track unexpected worker death (set in
     _worker_loop's except BaseException handler)
  2. Rewrote _ensure_worker() to be atomic under the lock:
     - Worker creation and start both happen inside the RLock
     - Checks _worker_gone flag alongside is_alive()
     - Does NOT clear _stopping (preserves shutdown semantics)
     - Returns False if _closed or _stopping.is_set()
  3. Rewrote _worker_loop() to:
     - Track BaseException death and set _worker_gone flag
     - Set _worker = None under lock when current thread dies
     - Call self.fail() to transition state to ERROR (instead of staying stuck
       in THINKING)
     - Drain any remaining queue items so _inflight returns to 0
     - Do NOT spawn a replacement worker (task_id is now terminal; next
       submit_task will spawn a fresh worker)
  4. Added second _ensure_worker() call in submit_task() after queue put to catch
     the case where the worker dies between the initial health check and the queue
     put

Regression tests added (tests/test_companion_worker_regression.py):
  - test_worker_death_is_recovered: BaseException death, next submission works
  - test_recovery_followed_by_successful_task: die on first, succeed on second
  - test_concurrent_submissions_around_worker_termination: drain + recover
  - test_repeated_submission_under_load: 20 rapid submissions, 1 worker

L1. REAL-MODEL FAILURE — RESOLVED
--------------------------------------------------------------------------------
Failure: test_the_goal_completed_and_the_artifact_is_observed_independently
         SHA-256 mismatch: expected fa33b88a..., actual 0ec52c4b...

Root cause: Category E — Windows newline translation in file-writing tools.
  On Windows, Path.write_text(content, encoding="utf-8") with default
  newline=None translates "\n" to "\r\n" (CRLF). The model was asked to write
  "diablo-real-model-autonomy-ok\n" (LF), but the file on disk contained
  "diablo-real-model-autonomy-ok\r\n" (CRLF).

  Evidence:
    Expected bytes: b'diablo-real-model-autonomy-ok\n'
    Expected sha256: fa33b88a8b97b116c0874cc5234ae3e69be3721ca5581813889ec63a73651ecf
    Actual bytes:   b'diablo-real-model-autonomy-ok\r\n'
    Actual sha256:  0ec52c4bf401f50c9f27ea372ca3b90427ff49f37412912e737c489ed9ed62d4
    Match: False

  The verification pipeline (observe_file_content) read back with read_text()
  which translates CRLF→LF, so content_match was True and verification PASSED.
  But the test reads raw bytes with read_bytes(), which sees CRLF, so SHA-256
  doesn't match.

  This is a real system defect (write_file silently modifying user data via
  platform-specific newline translation), not merely a model weakness.
