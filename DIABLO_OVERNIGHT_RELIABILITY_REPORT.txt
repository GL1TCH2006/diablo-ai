SECTION B: REAL-MODEL FAILURE INVESTIGATION

FAILING TEST:
  tests/test_m217_real_model_autonomy.py::
  TestRealModelAutonomy.test_the_goal_completed_and_the_artifact_is_observed_independently

FAILURE OUTPUT:
  AssertionError: real_goal_artifact.txt exists but does not contain the
  requested content (sha256 0ec52c4bf401f50c..., expected
  fa33b88a8b97b116...)

ROOT CAUSE: Category E — file-writing newline translation

On Windows, Path.write_text() with default newline=None translates "\n" to
"\r\n" (CRLF). The model was asked to write "diablo-real-model-autonomy-ok\n"
(LF), but the file on disk contained "diablo-real-model-autonomy-ok\r\n" (CRLF).

Evidence:
  Expected bytes: b'diablo-real-model-autonomy-ok\n'
  Expected sha256: fa33b88a8b97b116c0874cc5234ae3e69be3721ca5581813889ec63a73651ecf
  Actual bytes:   b'diablo-real-model-autonomy-ok\r\n'
  Actual sha256:  0ec52c4bf401f50c9f27ea372ca3b90427ff49f37412912e737c489ed9ed62d4
  Match: False

The verification pipeline (observe_file_content) read back with read_text()
which translates CRLF→LF, so content_match was True and verification PASSED.
But the test reads raw bytes with read_bytes(), which sees CRLF, so SHA-256
doesn't match.

This is a real system defect, not merely a model weakness. The write_file tool
was silently modifying user data via platform-specific newline translation.

Fix 1: Preserve exact bytes in write_file (tools/filesystem.py)
----------------------------------------------------------------
File: tools/filesystem.py
Change: target.write_text(content, encoding="utf-8")
        → target.write_text(content, encoding="utf-8", newline="")
Reason: newline="" prevents Windows CRLF translation, so the file contains
exactly the bytes the model requested.

Fix 2: Preserve exact bytes in read_file (tools/filesystem.py)
----------------------------------------------------------------
File: tools/filesystem.py
Change: target.read_text(encoding="utf-8")
        → target.read_text(encoding="utf-8", newline="")
Reason: newline="" prevents Windows CRLF→LF translation on read, so read_file
returns exactly what's on disk.

Fix 3: Preserve exact bytes in observe_file_content (core/verification.py)
--------------------------------------------------------------------------
File: core/verification.py
Change: resolved.read_text(encoding="utf-8")
        → resolved.read_text(encoding="utf-8", newline="")
Reason: newline="" prevents Windows CRLF→LF translation on verification read,
so the verifier compares exact bytes rather than translated text. Without this,
the verifier would PASS on CRLF content while the test sees mismatched bytes.

Fix 4: Test setup writes exact bytes (tests/test_m217_windows_path_edges.py)
----------------------------------------------------------------------------
File: tests/test_m217_windows_path_edges.py
Change: open(stream, "w", encoding="utf-8")
        → open(stream, "w", encoding="utf-8", newline="")
Reason: The ADS test wrote "stream-payload\n" with default newline (CRLF on
Windows), then expected observe_file_content to match "stream-payload\n".
With exact-byte verification, the test must write exactly what it expects to
verify. This fixes the test setup, not its expectations.

No test expectations were changed. No production code was hardened to
accommodate incorrect model output. The verification invariant is preserved:
content must match exactly, byte for byte.
