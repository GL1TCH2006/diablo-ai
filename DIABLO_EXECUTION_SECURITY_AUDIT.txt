SECTION 3: FINDINGS WITH EVIDENCE AND SEVERITY
================================================================================

FINDING 1: python.run_script has NO cancellation support
--------------------------------------------------------------------------------
Severity: HIGH (Verified vulnerability)
Location: tools/python.py:14-47, core/executor.py:292-310
Evidence:
  - run_script() uses subprocess.run() with timeout but NO cancellation_token parameter
  - Executor checks cancellation at 4 points (lines 171, 262, 280, 326) but python.run_script cannot be interrupted mid-execution
  - A long-running or hung Python script cannot be cancelled once started
  - Cancellation token passed to Executor.run() is ignored by python tool

Impact: User presses "Stop" → task marked cancelled → Python script continues running in background with full user privileges

FINDING 2: python.run_script executes with FULL USER PRIVILEGES, no sandbox
--------------------------------------------------------------------------------
Severity: HIGH (Documented design, not a bug)
Location: tools/python.py:17-19
Evidence:
  - Explicit comment: "NOT a sandbox - a Python script has Diablo's privileges"
  - Runs with sys.executable (Diablo's Python interpreter)
  - cwd = script's parent directory (not restricted to allowed_roots)
  - Script can import os, subprocess, socket, etc. and do anything user can do
  - Path containment only checked for permission LEVEL, not at execution time

Impact: Malicious or buggy script can read/write/delete any file user can access, make network connections, spawn processes

FINDING 3: terminal.execute - no process kill on timeout
--------------------------------------------------------------------------------
Severity: MEDIUM (Verified gap)
Location: tools/terminal.py:32-52
Evidence:
  - subprocess.run(timeout=timeout) raises TimeoutExpired
  - Tool returns error "Command timed out after Ns" but subprocess.run() DOES kill the process on timeout (Python 3.14 behavior)
  - However, NO cancellation integration: if user cancels during command, command continues
  - No explicit process group kill on Windows (subprocess.run uses CREATE_NEW_PROCESS_GROUP? No)

Wait - Python's subprocess.run DOES kill the child on timeout. But if cancellation is requested externally, the command continues.

Impact: Cancelled terminal commands may continue running

FINDING 4: Blender execute_script allows ARBITRARY PYTHON in Blender context
--------------------------------------------------------------------------------
Severity: HIGH (By design, powerful capability)
Location: blender/scripts/diablo_blender_ops.py:387-393, blender/capabilities.py:559-561
Evidence:
  - execute_script operation passes user script directly to exec() in Blender's Python
  - Blender Python has full bpy access + os, subprocess, socket, etc.
  - No sandbox, no restriction on imports
  - Runs in Blender process (separate from Diablo process)

Impact: Model can execute arbitrary code in Blender process. Blender process runs with user privileges.

FINDING 5: Blender execute_script - NO cancellation support during script execution
--------------------------------------------------------------------------------
Severity: MEDIUM
Location: blender/scripts/runner.py:80-88, blender/runner.py:304-441
Evidence:
  - Blender runner supports cancellation via cancel_token (polling loop)
  - BUT: during handler execution (ops.op_execute_script), the Blender Python runs uninterruptibly
  - Runner only checks cancellation BETWEEN operations, not DURING
  - Long-running execute_script cannot be cancelled mid-script

Impact: Arbitrary Blender Python script runs to completion even if user cancels

FINDING 6: Voice TTS - no cancellation, no interruption (barge-in)
--------------------------------------------------------------------------------
Severity: LOW (Documented limitation)
Location: voice/text_to_speech.py:48-60, voice/capabilities.py:35-38
Evidence:
  - speak() spawns daemon thread, returns immediately
  - now=True waits with 35s join timeout
  - No way to stop speaking once started (no SAPI async cancel used)
  - No barge-in: microphone not monitored during TTS
  - Documented in voice/capabilities.py:35-38

Impact: User cannot interrupt TTS; must wait for completion

FINDING 7: applications.open fallback uses PowerShell Get-Process polling
--------------------------------------------------------------------------------
Severity: LOW (Fallback path only)
Location: tools/applications.py:253-268
Evidence:
  - _confirm_process_powershell() runs Get-Process in loop (6x, 0.4s intervals)
  - Uses f-string with exe_base directly in PowerShell command (potential injection if exe_base untrusted)
  - exe_base derived from launch_path via os.path.basename → lower()

Risk: Low - exe_base comes from resolved executable path, not user input directly

FINDING 8: git command ref validation - defensive but incomplete
--------------------------------------------------------------------------------
Severity: LOW
Location: tools/git.py:30-32 (_valid_git_ref), line 75 (check-ref-format)
Evidence:
  - _valid_git_ref() rejects leading "-", control chars
  - git check-ref-format --branch validates branch name
  - BUT: remote/branch args in push/pull not validated same way
  - git_push/pul use _valid_git_ref on remote/branch (lines 129-132, 183-186)

FINDING 9: desktop workflow tools delegate to capability bridge with native calls
--------------------------------------------------------------------------------
Severity: INFORMATIONAL
Location: tools/desktop.py, tools/capability_bridge.py, integration/workflows.py
Evidence:
  - Primary path uses pywin32/comtypes (no subprocess)
  - Windows capability uses native Win32/UIA APIs
  - Cancellation supported via CancellationToken in tool_context
  - Some fallbacks use PowerShell (applications.py confirmation)
