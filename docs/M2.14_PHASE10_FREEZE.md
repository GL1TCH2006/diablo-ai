## 1. What closed Phase 10

Four pieces, in order.

**Phase 10A — the terminal verdict invariant.** Two live tests in
`tests/test_recovery_p10_real_model.py` asserted opposite things about a task
ending `COMPLETED` without a passing verdict, and the one that failed was
passing only because its `if` guard never fired. Traced through Agent →
TaskManager → ExecutionPlan → Executor → VerificationLedger → RecoveryPolicy →
finalization → TaskStore, the architecture already held the correct answer in
`TaskManager.task_succeeded()`. That answer is now written down once, as an
explicit invariant, and enforced at the state machine rather than asserted twice.

**Phase 10Q — final validation.** A 20-row matrix over the completed
architecture, with an authoritative component, expected result, evidence and test
location per row, and an explicit "not here, and why" section. It adds no
behaviour. It found two defects, both in real-model assertions that claimed to
test persistence and actually tested model behaviour.

**Phase 10R — architecture / security / boundary audit.** 44 properties across
the eight requested areas, each classified PASS / DEFECT / LIMITATION /
DEFERRED with evidence. Two defects, the same two 10Q found. No redesign.

**Phase 10 freeze.** This document, and the commit.

## 2. The contract decision

Recorded in full at
`docs/contracts/cross_layer_execution_contracts.md` § "M2.14 Phase 10A". The
short form:

```
TaskState        answers: did the request terminate, and how?
VerificationState answers: was the result independently checked?

COMPLETED asserts the first and never the second.
```

A task **can and does** enter `COMPLETED` with a non-`PASSED` verdict. That is
honest, not a false pass. Forbidden, and enforced:

* `COMPLETED` + `FAILED` — reports a failure as a finished request
* `FAILED` + `PASSED` — a pass surviving an execution failure

Success is reported tri-state: `True` only for `COMPLETED` + adjudicated
`PASSED`; `False` for `FAILED` state or an adjudicated `FAILED` verdict; `None`
for "no verdict was reached". `None` is never reported as `False`.

No new task state and no new verification state were added.
`TerminalVerdict` is a pure classification over the two existing vocabularies.

## 9. Remaining limitations

Carried forward unchanged. Restated so 10R cannot be read as having fixed them.

* **F3 / S2.8** — an already-running Blender child cannot always be
  interrupted; supervision is not bound directly to the task token. Recovery
  guarantees only that *where interruption is possible*, cancellation dominates.
* **B5** — intent-path ledger entries carry no `step_id`, and durable plan steps
  often hold an empty `verification_state`, so a verdict cannot always be
  correlated to one plan step.
* **G7** — `DebugLoop` offers a narrower tool set by hardcoded name, with no
  `knowledge.*`. No knowledge is lost: task and verification are projected by
  `_finish_tracking` on every path. Changing it would alter frozen routing.
* **G8** — real-model observations are one model per session. Phase 10Q's tool
  observation reproduced across two runs and two prompts; nothing broader is
  claimed.
* The Phase 9/10 handover §8 "do not fix merely because listed" set, unchanged:
  `resource_check_enabled=False`, no `[build-system]`, plan display-name
  collision, Blender running-child cancellation, knowledge withheld under strong
  coding/debug contexts.
* The pytest fixture deprecation in §7.

## 10. Deferred roadmap

Not started, not claimed, not in scope for Phase 10. Recorded here so the gap is
explicit rather than implicit.

* **`Agent.resume()`** — does not exist. Restart fails closed
  (`_reconcile_interrupted_tasks` marks interrupted work `failed`, never
  auto-resumes, emits `plan_step_interrupted` with `replayable=False`). The rule
  a future `resume()` must follow is now fixed: read `terminal_verdict`, never
  infer from `status == "completed"`, and never treat `COMPLETED` +
  `UNVERIFIED` as finished work.
* **Native Windows capability layer** — no `pywin32`, no window management, no
  mouse/keyboard, no UI Automation, no screen capture. `tools/applications.py`
  shells out to PowerShell `Get-StartApps` / `Get-Process`, and UWP launching is
  explicitly unsupported. M2.15.
* **A real STT backend** — `voice/stt/local.py` detects an installed dependency
  and raises `SpeechToTextUnavailable` on every call. M2.19.

## 12. Recommended next milestone

**M2.15 — Native Windows Systems Foundation.**

Not M2.16, and not desktop control directly. Diablo is strong internally —
reasoning, coding, task execution, verification, Git, Blender/Vision, memory, a
persistent knowledge graph — and has no native Windows capability layer at all.
M2.16 desktop control needs the process/window/ownership model that M2.15
establishes, so the order is architectural, not preferential.
