C.1 Root cause - and a correction to the previous audit
-------------------------------------------------------

The M2.16.UI audit reported real-model desktop-tool selection at 0/3 and
attributed it to the model preferring `applications.open`. That attribution was
wrong. Three defects were actually responsible, and only the third is about the
model at all:

  (1) No model was ever consulted.
      Planner.fast_intent matched ^(?:open|launch|start)\s+(.+)$ and returned
      applications.open *before* any LLM call. All three audited runs hit it. The
      audit's other observation - that 8b passed the whole sentence as the
      application name - was this same regex being greedy, not a model defect. The
      previous audit drew a model conclusion from a regex.

  (2) The desktop tools were unreachable by routing.
      Agent._requested_capabilities could only emit debugging, coding or
      version_control, so the "desktop" capability group could never be selected
      and desktop.* was never presented. A tool the model cannot see is a tool it
      cannot select.

  (3) The tool-context selector was dead in production.
      config/settings.py passed the *string* "false" through _str(...) as
      _as_bool's default for tools_full_context and resource_check_enabled.
      _as_bool returns its default unchanged when the env var is absent, so both
      settings were the truthy string "false". Agent._tool_context therefore called
      select(full=True) on every turn: the whole M2.13.0 selector was bypassed and
      the model received all 74 tools every turn. This had been silently disabling
      the selector since M2.13.0.

C.2 Changes
-----------

  core/desktop_intent.py (new)
    Eight bounded intent families: APPLICATION_LAUNCH, WINDOW_MANAGEMENT,
    UI_DISCOVERY, UI_ACTION, KEYBOARD_INTERACTION, POINTER_INTERACTION,
    SCREEN_DISPLAY, COMPOUND_DESKTOP_TASK, plus NONE. A table of compiled
    patterns and a pure function - no NLP system, no I/O, no clock, no
    randomness. A pure classifier is asserted by import test.

    Unclassified widens to the whole desktop surface and never narrows.

  core/planner.py
    fast_intent short-circuits only for a genuine single launch with an isolable
    name. Compound requests reach the model. Demonstratives ("Open this") are
    refused rather than launched, since they cannot name a program.
    "run" is deliberately NOT a launch verb: adding it would have routed "run my
    test suite" to an application launcher, a regression the old path never had.

  core/tool_context.py
    New `families` signal and a `focus_families` mode. The selector receives a
    resolved family name and never inspects user text, preserving the property an
    existing architectural test asserts. Only tool *names* are added for a family -
    adding the capability would pull in every tool sharing that namespace, and all
    five desktop tools share one, which silently defeated the bound.

  core/agent.py
    Classifies once per request, passes families plus focus, and records structured
    telemetry. Implements bounded wrong-tool recovery: when *every* desktop tool in
    a plan mismatches the request's family, the model is asked once more, within a
    settings budget. Telemetry is emitted whether or not a correction was spent.

  tools/__init__.py, tools/desktop.py, core/context.py
    applications.open now states it can only START a program and names the
    alternative. The desktop tools state when they apply, what they operate on and
    what they require. The system prompt no longer steers unconditionally at the
    legacy tool and now names the desktop route.

  config
    desktop_mismatch_corrections (default 1), desktop_focus_min_confidence
    (default 0.6), and the two pre-existing string-truthy bugs fixed.

C.4 Three measurement defects in my own harness
------------------------------------------------

Each of these made a working path look broken. They are recorded because the
previous audit's wrong conclusion came from exactly this class of error.

  (a) No capability runtime. build_registry without one registers no desktop.* tools
      at all, so the probe measured routing against an empty set. The first run
      reported "0 desktop tools offered".
  (b) Shared durable conversation. A fresh Agent per case was not enough, because
      ConversationStore is persisted and every new Agent restored the previous
      run's transcript. Each case was therefore answered by a model that had just
      read ten of its own earlier refusals ("Notepad must be manually opened") and
      reproduced them verbatim. Isolating memory_dir per run fixed it, and took
      correct routing from 6/12 to 10/12.
  (c) Only the last provider call was read. The agent loops; a first turn may
      select correctly and a later recovery turn contain prose. Reading only the
      last call reported "no selection" for requests that had already chosen well.

  Separately, the probe leaked real side effects: it intercepted _execute_step but
  not _run_intent, so two cases actually launched Notepad on this machine. Both
  paths are intercepted now, and the stray processes were cleaned up.

================================================================================
D. M2.17 - PERSISTENT AUTONOMY
================================================================================

D.1 The Goal is not a Task
--------------------------

TaskState is untouched. A Goal models an objective that outlives any single
attempt; a Task models one attempt. A Goal may produce many Tasks; a Task belongs
to at most one Goal. Overloading TaskState would make "this task is done" and "this
objective is achieved" indistinguishable, which is the conflation that lets an
agent claim success it did not earn.

  GoalState: CREATED, ACTIVE, PAUSED, RESUMABLE, COMPLETED, FAILED, CANCELLED
  Explicit transition table; nothing unlisted is permitted.

D.2 Durable storage
-------------------

One JSON file per goal under <sessions_dir>/goals/<goal_id>.json, written with
memory.storage.save_json - the repository's single atomic helper (temp file in the
same directory, then os.replace). Unsafe identifiers are refused. Records are
versioned. An unreadable record reads as *absent*, not as an empty goal, because
"no work ran" and "we cannot tell what ran" must not collapse into one answer.
Unknown fields survive a round trip in metadata rather than being dropped.

All free text is redacted with the same policy the companion uses, so a credential
typed into a goal cannot come back out of the store. Verified by reading the raw
file.

D.3 Agent.resume
----------------

The capability core/windows/__init__.py had recorded as absent. Nine steps:

  1-2  load durable state; interrupted steps already classified in __init__
  3    inspect the execution plan
  4    restore the VerificationLedger from its persisted projection
  5    restore recovery state
  6    classify what is resumable
  7    REFUSE uncertain side-effect replay
  8    rebuild normal request context and system prompt
  9    continue through the ordinary permission-checked execution path

Two properties worth naming:

  - Step 4 closes a documented gap. VerificationLedger.from_dict existed and was
    exercised only by tests; production never restored a ledger. A resume that
    could not see prior evidence would re-verify completed work.
  - Step 7 is the milestone's central safety rule. A step persisted RUNNING by a
    process death may or may not have applied its effect. PlanStepRecord already
    encodes this via interrupted and is_replayable; resume applies it to a whole
    task and BLOCKS the entire task rather than replaying the safe subset, because
    partial replay leaves a durable plan describing a world that never existed.

  Prior terminal state is read through terminal_verdict(state, verification),
  never from status == "completed". A reloaded COMPLETED + UNVERIFIED means the
  work was never checked and is not resumed as though it were done.

D.4 Scheduler
-------------

AutonomyScheduler decides only whether a due, authorised goal should start a Task,
and records that durably before submitting. It reaches tools solely through an
injected submit callback, which in production is the Agent's normal request path -
so there is no autonomous execution path that could be unsafe. Asserted by import
test: no core.executor, no core.windows, no tools.registry, no ctypes.

Idempotency is durable, not in-memory. Each goal carries last_started_tick keyed
on its own due instant, so a repeated tick, a restart mid-tick and two racing
schedulers all compare the same string and all decline. A wall-clock timestamp
would not do: two checks in the same second would produce different strings.

Persistence happens BEFORE submission. A crash between the two skips one run; the
reverse order would duplicate one. The schedule is advanced before the save, so the
persisted record already carries the next due time - an ordering bug found by test
that left the advance in memory only.

Every non-started goal is reported with a reason. Silently omitting a declined goal
would make one that never runs indistinguishable from one that does not exist.

D.5 Startup reconciliation
--------------------------

Deterministic: reads durable state, writes durable state, and decides nothing else.
Running it twice produces the same report - asserted.

  cancelled goal          left cancelled; restart never resurrects it
  awaiting permission     left paused; autonomy never auto-confirms
  recovery exhausted      surfaced as failed, not retried
  unauthorised            paused
  in-flight task          marked RESUMABLE - may be picked up, not that it will be
  task finished while down goal returns ACTIVE; its evidence is the goal's call

A task that completed while the process was down does NOT complete the goal. That
case is tested explicitly: a goal needing two evidences stays uncompleted after its
only task reports success.

D.6 Goal/task relationship and completion
------------------------------------------

  Goal completion requires len(verified_task_ids) >= required_evidence.
  Evidence recording is idempotent, so a repeated completion event cannot inflate
  the count toward completion.
  mark_completed() refuses without the evidence and the state does not move.
  Tested: "create the project and make all tests pass" with required_evidence=3
  stays ACTIVE after one task completes.

D.7 Cancellation
----------------

Durable and irreversible. cancel_requested is persisted the moment the user
cancels, is_schedulable() refuses it, the scheduler declines it with reason
"cancelled", and reconciliation leaves it cancelled. Tested across a restart.

D.8 Resource limits
-------------------

New [autonomy] settings: max_active_goals=3, max_tasks=32, max_concurrent=1,
min_interval_seconds=60. These are ceilings on how much may happen, never
permissions. Verified live: 40 due goals, the scheduler started exactly 3 and
declined the rest with a stated reason.

The checklist for this milestone says the limits must ride the *existing* gate, with
no second system. The first implementation did not, and the audit's original claim -
"no second resource-management system was created" - was the kind of sentence that
is technically defensible and practically misleading. ``AutonomyScheduler`` kept its
own ``_in_flight`` counter alongside ``BoundedRequestGate``, which is two
concurrency limiters in front of one Agent: one governing every request, one
governing only autonomous ones. The private counter could only ever have been a
policy ceiling dressed up as resource management, because it was incremented on the
same path the gate already serialises.

Now there is one limiter. The scheduler reads ``agent.request_gate.in_flight`` and
compares it against the policy ceiling; it never increments anything, and
``self._in_flight`` no longer exists. A test asserts its absence from the source, so
this cannot quietly grow back.

D.9 Companion integration
-------------------------

A bounded read-only projection: goal_line and goal_active on the existing
snapshot, rendered as one redacted line. The companion displays autonomous work and
has no authority over any goal. Tests assert it never grew a create, schedule or
cancel path, and that its state module does not import the goal model or the
scheduler - it receives a projection, not the authority.

And then, on the checklist's own wording, a second pass over this section found the
same defect as D.10: ``apply_goal_projection`` had twenty passing tests and **zero
production callers**. The projection was implemented, redacted, bounded, rendered -
and unreachable, because nothing ever handed it a summary.

The view now holds a ``goal_provider`` callable and pulls the newest summary on its
existing frame loop, throttled to once a second. No second timer and no second
thread: a companion that grows its own poll loop grows its own shutdown obligation.
``main.py`` passes ``autonomy_runtime.snapshot`` under ``--autonomy``. The seam is a
callable and never a GoalStore, which is asserted by inspecting the shipped source
rather than by convention - if the view ever reaches ``mark_completed`` or
``GoalStore``, a test fails.

This is the second time in one milestone that a fully-tested component turned out
to be unreachable, and the second time the tests were arranged so they could not
notice. The pattern is now stated explicitly in the test names:
``test_m217_companion_projection_wiring.py`` exercises the *path*, not the
destination.

D.10 The production runtime (added after the first audit draft)
----------------------------------------------------------------

Writing this section is itself a finding. The first draft of this audit described the
scheduler's submit callback as reaching "the Agent's normal request path in
production". That was **false when written**. A grep for importers of
``core.goals`` and ``core.autonomy`` across every non-test module returned nothing:
the goal layer was correct, comprehensively tested, and completely unreachable. A
durable feature that nothing can start is a feature that does not exist, and the
tests had been structured so that this was invisible - they injected their own
submit callback and therefore never needed a production one.

``AutonomyRuntime`` closes the gap. It owns the goal lifecycle in production:
reconcile, tick, submit, observe, cancel, project. Its permissions are narrow on
purpose:

* It creates a Task by calling the Agent's ordinary ``respond`` - the same entry
  point a typed user turn uses - and then *observes* the task record that call
  produced.
* It never executes a tool, mints a task id, auto-confirms a permission, decides
  success, or resurrects a cancelled goal.
* ``goal_completed`` is True only because ``Goal.mark_completed`` accepted
  accumulated *verified* evidence.

Wiring, opt-in and off by default:

    main.py --autonomy [--autonomy-interval 30]

Opt-in is the honest choice rather than a cautious one. A goal becomes a Task
without a user typing anything, so starting that unasked would be the surprise this
project is supposed to avoid. Reconciliation and the scheduler thread are created
only under the flag, and the thread is stopped through ``atexit`` so it cannot outlive
the capability runtime on any of the four UI exit paths.

Verified end to end, in a real process, against the real Agent:

    [autonomy] reconciled 1 goal(s); active: Report the free disk space ...
    [autonomy] scheduler running as diablo-autonomy-scheduler (every 3s)
    autonomy autonomy_goal_observed {'goal_id': 'smoke1',
        'task_id': 'cf426ea3f40e4e0fb563fff886168529', 'verdict': 'unverified',
        'goal_completed': False}
    autonomy autonomy_task_started {'goal_id': 'smoke1', ...}
    autonomy autonomy_tick {'started': 1, 'due': 1, 'skipped': 0, 'errors': 0}
    autonomy autonomy_tick {'started': 0, 'due': 0, 'skipped': 1, 'errors': 0}
    ...
    state: active | task_ids: ['cf426ea3f40e4e0fb563fff886168529']
    last_started_tick: 20200101-000000 | next_run_at: 20261003-170903

The task id came from the TaskManager's own minting path. The first tick started the
goal; every later tick declined it with "not due" and wrote nothing.

Four defects this work exposed, all fixed, none of them hypothetical:

1. **A goal could never be completed by a direct submit.** The scheduler transitions
   a goal to ACTIVE before submitting, so a tick-driven start was fine. Any other
   caller - the real-model probe, an operator script, a test - arrived with the goal
   still CREATED, and CREATED cannot reach COMPLETED through the transition table.
   The runtime could not complete the goals it was asked to run. Fixed in ``observe``.
2. **Every in-flight task read as "unknown".** ``TaskRecord.status`` says
   "pending"/"active"; ``TaskState`` says CREATED/EXECUTING. Passing a record status
   straight into ``terminal_verdict`` raises, and the exception was degraded into
   "unknown" - so a task still running looked unreadable, and would never have
   contributed evidence. Fixed with an explicit, listed translation table.
3. **Free-form ``metadata`` was persisted unredacted.** Every other field went
   through ``sanitize_goal_text``; ``metadata`` was written with
   ``dict(self.metadata)``. A caller-supplied
   ``{"headers": {"Authorization": "Bearer ..."}}`` landed on disk in the clear while
   this audit claimed goals redact on write. Now walked recursively, with a depth
   cap and an entry cap.
4. **``ReconciliationReport.changed`` counted decisions, not changes.** Every startup
   reported "N goals changed" for goals already exactly where reconciliation wanted
   them. Now tracks goals whose persisted state actually moved, separately from the
   decision lists.

A fifth problem was in a test rather than the code. The ledger-restore test built an
**empty** ledger - its helper ignored its argument - and then asserted
``report.ledger_entries >= 0``. It could not fail, and it read like coverage of the
exact gap M2.17 claims to close. It now persists a real one-entry ledger and asserts
the restored count, state and evidence.

And one caution about the CLI evidence above: the first three attempts to reproduce
it reported "the scheduler never ticked", which was the harness, not the code. The
console UI reads stdin, and a headless launch gets EOF immediately, so the process
exits about a second after startup - before the first tick. Two of those runs also
seeded the goal into a directory the settings never read. Both failures looked
exactly like a broken feature. The lesson is the same one as in section C.4: check
that the harness can observe success before believing it observed failure.

  Read the file <abs path>            filesystem.read_file unverified     n         n

Three results in phase B are worth stating plainly, because two of them look like
failures and are not.

**0/3 goals completed, and that is the system working.** The two file operations ran
for real and finished, but the task record says ``unverified`` - "No independent
verifier was available" - and ``unverified`` is not evidence. Under a real model,
on a real run, a goal stayed ACTIVE because nothing had verified its work. That is
Â§35 doing exactly what it exists to do, and it is the single most valuable piece of
evidence in this milestone: the anti-overclaiming property is not a claim, it is
observable behaviour.

**One goal was cancelled, correctly.** ``terminal.execute`` needs confirmation, and
``--autonomy`` runs without an interactive channel, so the step was cancelled rather
than run. Autonomy did not acquire a way to answer its own permission prompts.

**A relative path would have produced two more cancellations.** An earlier run of
this phase scored 1/3 with every step cancelled. The cause was not autonomy: a
relative path resolves against the process working directory rather than
``workspace_root``, so it lands outside ``allowed_roots``, is judged SENSITIVE, and
is then cancelled for want of a confirmation channel. Absolute in-root paths execute
without any prompt. Recorded because an autonomy probe using relative paths measures
refusals while appearing to measure execution - the same class of error as C.4 and as
the fast-path miscount below.

A fourth measurement flaw, in this probe: goals answered in ~10ms with no tool call
were being scored as "the model chose nothing". They had been answered by the fast
path, and the model was never asked. The probe now distinguishes *answered wrongly*
from *never asked*, and reports the split (model 3, fast path 0). That is the third
time in this milestone that a harness error looked like a model failure.

E. SECURITY AUDIT
================================================================================

  Permission bypass        NO. Autonomy has no execution path. Every task goes
                            through the existing TaskManager and PermissionManager.
                            A goal awaiting permission is declined with reason
                            "awaiting permission" and is never auto-confirmed.
                            Real-model run 2 of the earlier audit showed a
                            confirmation-requiring tool correctly refused.
  Scheduler bypass         NO. The scheduler's entire surface is an injected
                            callback. Import-tested: no executor, no windows, no
                            tool registry, no ctypes.
  Resume replay            NO. A side-effecting interrupted step blocks the whole
                            task. Proven across a real process restart.
  Task identity            NO. The scheduler generates no task id; the TaskManager
                            mints it. A goal cannot supply one.
  Request identity         NO. Unchanged; the UI-chosen id is still not forwarded.
  Secret persistence       NO. Goals redact on write with the companion's policy;
                            verified by reading the raw file for the secret.
  Prompt injection         NO. Persisted goal text is data. It is read back as task
                            input through the normal request lifecycle, and the
                            goal record exposes no field that could be mistaken for
                            policy (no system_prompt, no policy).
  Native handle leakage    NO. Handle-shaped literals are redacted and the modules
                            import no native API.
  Target spoofing          NO. Unchanged from M2.16.5/6; autonomy adds no targeting.
  Companion isolation      NO. Read-only projection, asserted by import and
                            attribute tests.
  Event telemetry          Redacted and structured: intent family, confidence, tool
                            counts, selected tool, mismatch flag. Never user prose.
  Verification bypass      NO. Goal completion requires accumulated evidence.
  Cancellation bypass      NO. Durable, restart-safe, checked in three places.
  Runtime reach            The goal layer is reachable only through --autonomy,
                            which is opt-in, and only ever calls Agent.respond.
                            Verified by a real CLI run: a due goal produced a
                            TaskManager-minted task id and no other execution.
  Runtime adjudication     NO. The runtime copies the verdict that
                            terminal_verdict computes from the task's own durable
                            lifecycle. It cannot turn an unverified completion into
                            evidence; asserted against a real Agent.

FINAL VERDICT
================================================================================

M2.16.UI, M2.16.UI.1 and M2.17 are COMPLETE WITH LIMITATIONS.

The central architectural claim held: there is still exactly one Agent, one
TaskManager, one TaskStore, one Executor, one PermissionManager, one
VerificationLedger, one cancellation protocol and one capability layer. The goal
layer records intent and authorisation and routes work through them; the scheduler
can only ask for a task; the companion can only display. Each of those is asserted
by test rather than by comment.

The most valuable outcome is the correction. A previous audit reported that a model
would not choose the desktop tools, and built a recommendation on that. The model
was never asked: a regex answered first, and a truthy string had disabled the tool
selector entirely. Fixing the three defects moved real-model selection from a
measured 0/3 to 10/12 with desktop tools chosen in half the cases.

The second correction is this one. The first draft of this audit described the goal
scheduler as feeding "the Agent's normal request path in production", and a grep
showed that no production module imported the goal layer at all. The tests had been
arranged so that this could never show up. Building the runtime then exposed four
defects that only exist on the real path - a goal that could never complete, an
in-flight task that read as unreadable, metadata persisted unredacted, and a change
counter that counted decisions rather than changes - plus a test that could not fail.
The lesson generalises past this milestone: a layer that is only ever exercised
through an injected seam is a layer whose integration is unproven, no matter how many
of its own tests pass.

The most important guarantee is negative and is proven across a real process
boundary: a step interrupted by a crash, whose side effect may already have applied,
is refused rather than replayed, and the whole task is blocked rather than
partially resumed.

What is not claimed is as long as what is. Selection improved materially; it is not
reliable. Autonomy is proven deterministically, across restarts, and against a real
Agent - but never against a real model on a real schedule. The real-Windows gate is
green on the final tree, and the one test that failed on an earlier run of it is
named, diagnosed as environmental, and not declared fixed.
