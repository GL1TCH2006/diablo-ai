   do next and dangerous to skip.

5. WHAT MUST M2.15 CONTAIN?
   - pywin32 dependency, declared in pyproject.toml and requirements.txt
   - core/windows/ package: process (enumerate, query, ownership, terminate),
     window (enumerate, titles, handles, focus), system metrics (native,
     replacing the PowerShell CIM path)
   - window/ and process/ capability adapters registered through
     CapabilityRegistry - the model calls capability.execute, never raw OS APIs
   - Permission classification per operation, following the existing
     SAFE/NORMAL/SENSITIVE/BLOCKED ladder
   - Cancellation bound into every long-running operation, as
     integration/contracts.py:_scopes already does for direct calls
   - Verification evidence per operation, through the existing ledger
   - Deterministic tests plus a real-Windows integration gate

6. WHAT MUST M2.15 NOT CONTAIN?
   - NO mouse, keyboard, screen capture, or UI Automation. Those are M2.16.
   - NO desktop automation semantics. M2.15 is a SYSTEMS layer, not a CONTROL
     layer.
   - NO changes to frozen architecture. If a defect surfaces, minimal
     compatible fix only.
   - NO second permission system, second ledger, or second recovery layer.
   - NO ctypes where pywin32 provides it. ONE native idiom, not two.

7. WHAT SHOULD M2.16 DEPEND ON?
   M2.15, ENTIRELY.
   Screen capture needs a screen abstraction.
   Window focus needs a window layer with an ownership model.
   Visual grounding needs a working VLM, which needs process supervision for
   GPU model processes.
   NOTHING in M2.16 is startable before M2.15.

8. WHAT SHOULD M2.17 DEPEND ON?
   M2.15 for process supervision (a long-running desktop task needs a supervisor
   that survives across turns).
   M2.21 IS BETTER AFTER M2.17 THAN BEFORE IT - long-horizon autonomy over
   desktop actions is much harder to bound safely than long-horizon autonomy
   over git and tests, which Diablo already does.

9. SHOULD ANY MILESTONE BE MERGED, SPLIT OR REORDERED?

   SPLIT M2.18.
   "Advanced Blender + Vision" is TWO UNRELATED PROBLEMS.
   Blender needs better session/state management.
   Vision needs a real VLM plus a fixed compare_images metric.
   Recommend M2.18a VISION FOUNDATION (working VLM backend + fix the diff
   metric + stop over-advertising) and M2.18b BLENDER DEPTH.
   Vision is the weaker half and blocks more.

   M2.19 (STT) BEFORE M2.20 (Companion UI) IS ALREADY CORRECT - and now MORE
   correct, because the companion UI cannot be meaningfully "advanced" without
   a working STT feeding it, and its current "listening" state does not even
   exist in ui/models.py.

   MERGE M2.21 INTO M2.15.
   "Additional App/API Integrations" is largely what M2.15's
   process/application layer enables. Once a native process layer exists, most
   integrations become tool registrations against it. Keeping M2.21 separate
   defers work M2.15 will largely do anyway.
   Recommend folding the FIRST BATCH into M2.15 and reserving M2.21 for genuine
   third-party APIs.

   ADD A CLEANUP MILESTONE - M2.14.1 HOUSEKEEPING (small, BEFORE M2.15):
   - wire or retire DevWorkflow
   - add a companion-UI entry point or mark S2.4 partial
   - apply redact to memory writes
   - make memory/rules writes atomic
   - fix Rule.scope
   - refresh README.md
   Six small, evidence-backed defects. Cheap now, and they remove traps before
   a new subsystem lands.
