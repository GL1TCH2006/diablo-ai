## 2. The defect

A repair loop reported a **correct** repair as still broken, intermittently.

CPython validates a cached `.pyc` against the source's modification time in
**whole seconds** and its **byte size**. An edit that preserves a file's length
and lands in the same second as the previous test run leaves a cache that looks
valid, so the next run imports the pre-repair module.

Reproduced 2 of 3 attempts under a real agent loop doing edit-then-verify in
quick succession. For a human this is a confusing "my fix did nothing". For the
repair loop it is worse: the model is told its correct repair failed, so it tries
something else, and the loop spends its budget chasing a defect that was
already fixed.

**The fix** is in `coding/test_runner.py:_bytecode_cache_prefix()`. `_run` now
points `PYTHONPYCACHEPREFIX` at a fresh `tempfile.mkdtemp(prefix="diablo-pycache-")`
for every invocation, so the verification subprocess never consults the project's
own bytecode cache. What it imports is always what is on disk. Nothing in the
project is deleted or modified; the caches it already has are simply not used for
that run. Reproduced 0 of 3 after the change.

This is the single production change in the phase, and it is the reason the
phase exists.

### 5.2 qwen3:14b vs qwen3:8b

The single real repair run took **222.35s**, inside the 200-370s the handover
recorded for qwen3:8b and well under the 278s it recorded for 14b in Phase 9.
A 14B model on this machine is not slower than an 8B one for this workload, so
the model-size cost the handover implies is not a finding worth carrying
forward.

The behavioural difference is the opposite of a capability difference, and is
the more useful observation: **qwen3:14b is less willing to call a tool at all.**
On qwen3:8b, a restarted process declined `knowledge.query` 3 times out of 3 but
still reached for `project.files`, then `task.list`, then `project.grep` — wrong
tool, real tool. On qwen3:14b the same cross-session prompt produced **zero
tool calls**: `steps == []`. The model answered a question about knowledge it
could only have obtained from a tool, without calling one. That is a stronger
form of the same weakness, and it is a fact about the model, not the harness.

### 5.3 Timeout caveat

`DIABLO_P9_TIMEOUT` was reduced from 900 to 240 for this run. This does not
change any assertion in the module, because `TURN_TIMEOUT` is a per-turn bound,
not a total. It does change one derived bound:
`test_an_unrepairable_project_stays_bounded_and_honest` asserts
`elapsed < TURN_TIMEOUT * 3`, which was a 2700s ceiling and is now 720s. The
observed elapsed was 239.82s, so the assertion passed comfortably either way and
no test was starved of time. **But the timings in §5.1 are not strictly
like-for-like with the handover's 8B figures**, which were taken at 900s, and
should not be differenced against them.

## 6. The two failures, diagnosed

Neither is an architecture regression. Both are defects in the test file itself,
and both are recorded here **unfixed**, because fixing them is a design
decision, not an observation.

### 6.1 `test_a_second_process_discovers_the_first_processs_knowledge`

Failed at `tests/test_recovery_p10_real_model.py:538` on
`the restarted process consulted nothing about the project: []`.

Every persistence assertion in the test **passed** before that line: process 1
left a knowledge database, the graph holds a task, `calc.py` is indexed, and
process 2 ran a real model. The test failed only because `consulted` was empty,
and it is empty because 14b made no tool calls at all (§5.2).

So this is **not** a persistence failure and should not be recorded as one. It
is the same class of observation the handover already recorded for 8b — the
model declining the tool it was told to use — taken one step further. The test
at line 534 requires *some* project-inspecting tool from a set of six; 8b
satisfied it with the wrong tool, 14b did not satisfy it at all.

> **RESOLVED by 10Q.** This diagnosis was correct. 10Q additionally found that
> the *next* assertion in the same test — that the task count was unchanged
> after the second session — was false by design, since every request projects
> its own task node. Both are now reported rather than asserted, and the
> persistence they were protecting is asserted structurally in
> `tests/test_phase10q_validation.py`. The module is now 21/21.

The file's own docstring (lines 470-484) argues at length that tool choice
should be reported rather than asserted, because the alternatives are defensible
answers. The persistence proof at lines 497-520 is sound and passed. The
assertion at 538 is the one that failed, and it asserts tool *usage*, not
persistence.

### 6.2 `test_an_unrepairable_project_stays_bounded_and_honest`

Failed at `tests/test_recovery_p10_real_model.py:620` on
`completed without a passing verdict`.

This is a **contradiction inside a single test file**, and it is the more serious
of the two findings.

The honesty assertions in the same test **passed**. The run was bounded, the
verification was correctly *not* `PASSED`, and no `PASSED` ledger entry lacked
evidence. The impossible suite was not converted into a pass, which is the entire
point of the test.

It failed on:

```python
if agent._tasks.state.value == "completed":
    assert agent._tasks.verification is VerificationState.PASSED
```

The model ran out of budget against a test nothing can satisfy, and the task
ended `COMPLETED` with verification `UNVERIFIED`. Line 620 reads that as a
contract violation.

But 287 lines earlier, in the same file (line 333), `10H`'s
`test_an_unverified_task_is_labelled_unverified_not_complete_as_verified`
asserts the **opposite**, and passed in the same session:

> Task completion and verification are separate facts. The turn can finish while
> the work was never independently checked, and that is an honest outcome rather
> than a false one: the architecture keeps the two apart instead of letting
> "completed" imply "verified".

The handover §4 records the same position as settled design: "A task can end
`completed` with verification `UNVERIFIED`. That is honest, not a false pass; the
two facts are kept separate by design."

Two tests in one file cannot both be right, and 10H is the one that matches the
documented design. Line 620 encodes a superseded assumption, from an earlier
version in which completion did imply verification. It was passing before only by
luck: it is conditional on the terminal state the model happened to reach, and
8b evidently landed on a non-`completed` state where the branch never ran. The
14B run reached `COMPLETED`, the branch executed, and the stale assumption
surfaced.

**This test was never actually validating anything.** Its `if` guard made the
assertion unreachable for one whole model class, so 8b passing it proved nothing
about the bounded-exhaustion contract.

Left unfixed, per the handover's §8 instruction not to "fix" listed limitations
on sight. This is not a listed limitation, though — it is a contradiction
between two live tests, and the earlier note does not obviously cover it. It
wants a decision, recorded, about what a `COMPLETED` task with `UNVERIFIED`
verification is supposed to mean. Whichever way that goes, one of lines 620-621
and 333-338 has to go with it.

**RESOLVED by Phase 10A.** The decision went to 10H: a task can end `COMPLETED`
with verification `UNVERIFIED`, and that is honest. Lines 619-621 now assert the
invariant's actual forbidden direction (`COMPLETED` + `FAILED`) instead of the
superseded assumption. The decision is written down once, enforced at the state
machine, and documented at
`docs/contracts/cross_layer_execution_contracts.md` § "M2.14 Phase 10A". Pinned
by `tests/test_terminal_state_invariant.py`. The module is now 21/21 — see
`docs/M2.14_PHASE10_FREEZE.md` §7.

## 7. What this phase proves

- The stale-bytecode defect is real, is reachable from the real repair loop, and
  is fixed at its source (`coding/test_runner.py`) rather than worked around.
- The fix is a one-file, 26-line change with no effect on 2164 other tests across
  two full runs, `compileall`, `pip check` and real Blender.
- A real local model, given a project broken on purpose and a prompt that never
  mentions the defect, reads the code, runs the suite, diagnoses the cause and
  repairs it — through the real Agent, registry, Executor, PermissionManager,
  RecoveryPolicy, VerificationLedger and knowledge projection, with nothing
  stubbed below the model.
- Failures reach the policy as structured observations with categories; recovery
  is bounded and counted; a pass is claimed only with observed evidence; a
  failing suite is never reported as a pass; the graph never claims more than the
  ledger recorded; the repaired source is what the graph indexed; the task record
  survives a restart; knowledge written by one process is readable by another.
