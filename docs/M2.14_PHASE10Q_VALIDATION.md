# M2.14 Phase 10Q — Final Phase 10 Validation

**This is a new milestone.** Neither 10Q nor 10R existed before this one. Phase
10's own sections run 10A to 10N; the Phase 10 handover listed "10Q/10R formal
regression + architecture audit" as outstanding without ever defining a subject
for them, and the Phase 10 report recorded that as undeliverable rather than
inventing one. This document and `docs/M2.14_PHASE10R_AUDIT.md` are that
definition, written now and executed against the repository as it stands.

## What 10Q is

A validation matrix over the **completed** Phase 10 architecture. 10Q does not
add behaviour. It answers one question per row: *is this thing actually
validated, by what, and is that validation load-bearing for closing Phase 10?*

A row marked NOT IMPLEMENTED is a legitimate 10Q result. Padding the matrix with
rows the system does not have would defeat the purpose.

## Legend

* **Required for closure** - Phase 10 cannot honestly close without this row.
* Deterministic rows run in the normal suite. Real-model rows need
  `DIABLO_REAL_MODEL_TESTS=1` and are skipped otherwise by design.

## Rows that are deliberately NOT here

Recorded so the omission is visible rather than accidental:

* **`Agent.resume()`** — does not exist. Row 8 covers what restart *does* today
  (fail, do not auto-resume). Resuming persisted work is a future milestone.
* **Real-model tool *selection* fidelity** — not asserted, only reported. Phase 9
  and Phase 10 both found real models declining or substituting tools, and the
  alternatives are defensible answers. Asserting a specific tool name would test
  the model, not the architecture. See 10R finding `DEFECT-1` below.
* **Native Windows / desktop control** — not implemented at all. Out of scope for
  Phase 10 closure; it is M2.15+.

## Finding raised by 10Q

10Q raised two defects. Both are in real-model assertions about **model
behaviour** that were really making claims about **persistence**, and both were
found by running the matrix rather than by reading it.

### DEFECT-1 — a tool-selection assertion was unreachable, and asserted the wrong layer

`test_a_second_process_discovers_the_first_processs_knowledge` asserted that the
restarted process consulted *some* project-inspecting tool. That is a fact about
the model, not about persistence. qwen3:14b made zero tool calls and failed the
test while **every persistence assertion around it passed** — process 1's
knowledge database, the task node, the indexed file. The class docstring already
argued at length that tool choice should be reported rather than asserted,
because `project.files`, `task.list` and `project.grep` are all defensible
answers to the question asked.

Resolution: the tool choice is printed as an observation. The persistence claim
it was protecting is now asserted structurally in
`tests/test_phase10q_validation.py`, against the store rather than against the
model's choices.

### DEFECT-2 — a "read-only session changed the data" assertion was simply false

The same test asserted that the task count was unchanged after the second
session. It is not unchanged, and it should not be: process 2 ran a full
`Agent.respond`, and **every request projects its own task node** — the
behaviour this same module already relies on above, where it asserts the graph
holds a task "without any help from the test". The count grew by exactly one,
which is precisely correct behaviour.

The assertion was wrong about what process 2 did. Replaced with the narrower and
stronger claim that was actually worth making: no node process 1 recorded was
lost (`before_ids - after_ids` empty), the count grew by exactly the second
session's own task, and the structural file knowledge survived. Both directions
are now checked.

Neither defect was an architecture fault. Both were tests asserting a fact about
a model where they claimed to assert a fact about a store. This is the same
class as the Phase 10A contradiction, and it is why 10Q executes its rows rather
than only tabulating them.
