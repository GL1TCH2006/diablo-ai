4. ARCHITECTURE SUMMARY
--------------------------------------------------------------------------------

    Companion UI  (ui/edge_companion.py - Tk, borderless, topmost)
         |  reads CompanionSnapshot; submits text; requests cancel
         v
    Companion Controller  (ui/companion_state.py - no tkinter import)
         |  submit_task / cancel / get_state / get_current_task
         |  subscribe_events / shutdown
         v
    ui/companion_events.py   narrow + redact  ->  CompanionEvent
         |
         v
    ui/bridge.py  (AgentBridge / CoreEventBusBridge - PRE-EXISTING)
         |
         v
    Agent -> TaskManager -> Executor -> Capability Layer -> Windows

Four properties are enforced structurally rather than by convention:

1. The logic imports no toolkit. ui/companion_state.py and ui/companion_events.py
   contain no `import tkinter`, so the entire state machine is testable with no
   display. The view renders a snapshot and cannot reach past it.

2. There is one event vocabulary boundary. Everything the backend emits passes
   through ui/companion_events.py, which recognises the conceptual Part 10 names,
   the AgentEvent types the existing bridge emits, and UIStatus values; drops
   anything unmapped; and redacts every string.

3. Task identity belongs to the backend. The companion keeps its own job id for
   display and staleness, and ui/launch.py's submitter deliberately does not
   forward it to Agent.respond.

4. Backend work never runs on the UI thread. One lazily-created daemon worker
   ("diablo-companion-submit") performs submission; the view only polls snapshots.

--------------------------------------------------------------------------------
5. STATE MACHINE
--------------------------------------------------------------------------------

Seven states, matching Part 3 exactly:

    SLEEPING -> AWAKENING -> LISTENING -> THINKING -> EXECUTING
                                                      |         |
                                                      v         v
    SLEEPING <- RETURNING <- (task_completed | ERROR <-(task_failed)
    (also <-   (also <-        task_cancelled)

CompanionState.THINKING -> EXECUTING moves only when the backend reports real
execution progress, never on submission.

Notable decisions, and why:

* Cancellation is a REQUEST, not an outcome. cancel() asks the backend to stop and
  sets cancellation_requested. The companion does not move to a terminal state
  until the backend says so. A task that completes after a cancel request is
  reported as completed, because that is what happened.

* SLEEPING is reachable from every state, so retract() is total. "Go back to the
  edge" can never silently fail. Hiding mid-task is safe because SLEEPING ->
  EXECUTING is not a permitted transition, so a late backend event cannot wake the
  companion against the user's wishes.

* Terminal task ids are remembered. A task that reached a terminal state cannot
  emit again, which is what makes it safe for a user to reopen the companion to
  read a result without losing task state (Part 14) and without a late event
  dragging the reopened companion back into EXECUTING.

* Lifecycle events (awakened/retracting/sleeping) are excluded from the task
  progress list by an explicit kind set, so a just-finished task does not show a
  "Sleeping" entry as its last line of progress.

--------------------------------------------------------------------------------
6. EDGE DOCKING AND SLEEPING BEHAVIOUR
--------------------------------------------------------------------------------

Placement is pure arithmetic in ui/edge.py over the M2.16.4 display abstraction:

* Rectangles derive from work_area, never bounds, so the companion never lands on
  the taskbar.
* The monitor is chosen by cursor position, falling back to primary only when the
  pointer is unavailable. It does not assume primary (Part 16).
* All four edges supported; unknown edge names fall back to "right" rather than
  raising.
* DPI scale is read from DisplayInfo and clamped to [1.0, 2.0] so an absurd value
  cannot produce an invisible or screen-filling window.
* The sleeping footprint is a genuine sliver. At 100% that is 74x34 fully
  retracted with ~62x34 still inside the work area; extended is 420x340. The
  sleeping form is under a quarter of the extended area.

A deliberate deviation, stated plainly:

  Part 5 asks for click-through "except on the companion itself", and Part 15
  requires a deterministic activation method. WS_EX_TRANSPARENT delivers the
  first and destroys the second, because it swallows the click on the companion
  itself. The compromise chosen is:
    - a genuinely tiny sleeping footprint, so it cannot meaningfully intercept
      input anywhere else;
    - WS_EX_NOACTIVATE while sleeping, so the presence never steals focus from the
      application the user is working in, and clicking it activates the companion;
    - WS_EX_TOOLWINDOW always, so it stays out of the taskbar and Alt-Tab;
    - NO global keyboard hook, NO global mouse hook, NO desktop-wide hit testing.

Verified negatively by test: the module contains no SetWindowsHookEx,
RegisterHotKey, WH_KEYBOARD_LL, WH_MOUSE_LL, GetAsyncKeyState or GetKeyState.

The single native call in the milestone is GetWindowLongW/SetWindowLongW on the
companion's OWN hwnd, which Part 8 and Part 29 explicitly permit for the companion
window itself. It is confined to one small class (_WindowStyle) and is
best-effort: on a host where it fails, the companion still runs.

7. EVENT STREAM AND REDACTION
--------------------------------------------------------------------------------

The backend's raw event language is much wider than a person needs to see.
ui/companion_events.py is the only place that decides what is safe to render.

Recognised inputs
  - the conceptual Part 10 names (REQUEST_ACCEPTED, TASK_CREATED, PLANNING,
    TOOL_SELECTED, STEP_STARTED/COMPLETED, VERIFICATION_STARTED/COMPLETED,
    RECOVERY_STARTED, CANCELLATION_REQUESTED, TASK_COMPLETED/FAILED/CANCELLED)
  - the AgentEvent.type values the existing bridge emits (status, activity,
    success, cancelled, error)
  - UIStatus values carried on generic envelopes
  - tool-level status, which takes priority

Deliberately NOT mapped
  - "ready" / "idle" / "closed" status heartbeats: they say nothing a user needs,
    and mapping them made the progress list flicker.
  - a tool reporting "cancelled": that is one tool's outcome, not the task's. The
    task-level terminal event is still to come, and rendering it as a cancellation
    would make the companion claim an outcome the backend never reported.

Redaction applied to every rendered string
  - credential-shaped assignments (api_key, token, password, secret, bearer,
    authorization, session_key, ...) in punctuation AND prose forms
    ("my api key is VALUE")
  - bare provider keys (sk-, rk-, ghp_, gho_, xox*, ...)
  - Authorization: Bearer <jwt>
  - labelled native handles (hwnd, handle, runtime_id, process_id, pid, ...)
  - bare 0x... addresses
  - newlines and control characters, collapsed to one line
  - length caps: 240 chars for a message, 60 for a progress summary

Metadata policy
  AgentEvent.metadata carries the backend's ENTIRE raw source event. The mapper
  reads exactly three keys from an explicit allowlist - tool, tool_status, detail -
  and never reads source_event. An allowlist rather than a denylist, because a
  denylist silently forwards whatever nobody thought to forbid.

  ui/bridge.py::_on_tool was extended to populate those three keys. The existing
  `message` format was NOT changed, because a pre-existing test
  (test_floating_companion.py) asserts on it and Part 35 forbids weakening tests.
  This is what lets the companion show "Opening Calculator" and distinguish a
  permission prompt from ordinary progress.

8. BACKEND LIFECYCLE - THE PART 18 DECISION
--------------------------------------------------------------------------------

Chosen: (A) attach in-process to the Agent the companion is handed.

Not (B), and not (C). A separate backend process would mean a second Agent, and a
second Agent is precisely what Part 10 and Rules 13-16 forbid. The repository's
Agent entry point is already in-process and already the single owner of the request
lifecycle, so the companion attaches to it and starts nothing.

Consequences, stated as facts:
  - the companion spawns no child process, so there is no orphan to manage;
  - the floating companion (--companion) and the edge companion
    (--edge-companion) are two presentations of ONE backend. A bridge may be
    passed in and is then deliberately NOT closed by the edge companion, so
    neither view owns it;
  - there is exactly one submitter, one canceller and one subscription set.

--------------------------------------------------------------------------------
9. THREADING
--------------------------------------------------------------------------------

UI thread (Tk mainloop): rendering, input, the frame timer, and nothing else.
Backend work: the existing Agent and task execution.

Backend submission happens on exactly one lazily-created daemon worker named
"diablo-companion-submit", fed by a queue. submit_task hands over a work item and
returns immediately.

This was a real defect found and fixed during this milestone: submission
originally called the bridge inline, and the view calls submit_task from Tk's
main thread, so the UI sat inside Agent.respond for the length of a whole model
and tool turn. With a real model that is tens of seconds of frozen companion -
a direct Part 19 violation. Regression cover: seven tests, including one that
asserts submit_task returns in under 0.5s against a deliberately blocked bridge.

Shutdown stops the worker with a sentinel and a bounded join, so no thread
outlives close() even when the backend is mid-turn. Verified after 8 full
companion cycles: thread delta 0.

The worker catches Exception, not BaseException. Swallowing KeyboardInterrupt or
SystemExit inside a daemon thread would be worse than letting it end; what matters
is that the controller RECOVERS, which it does because _inflight is decremented in
a finally and the next submission starts a fresh worker. Tested.

13. DEFECTS FOUND BY VALIDATION AND FIXED
--------------------------------------------------------------------------------

Every item below was found by a test or a measurement, not by inspection.

In code written during this milestone:
  1. STOP vanished the instant it was pressed. Visibility keyed off `can_cancel`,
     which goes false once a cancellation is registered - so a registered request
     was indistinguishable from a lost one. Now keyed off
     `cancellation_requested`, relabelled STOPPING.
  2. retract() was refused from THINKING and EXECUTING. "Go back to the edge"
     could silently fail. SLEEPING is now reachable from every state.
  3. activate() during RETURNING wiped the task and the result, violating Part 14
     ("do not lose task state"). Fixed, with terminal task-id tracking so the
     retained id cannot receive further events.
  4. A zero peek/dwell window meant "never fire" instead of "fire immediately",
     leaving the companion stuck in RETURNING forever when animated with no
     delay.
  5. Lifecycle events polluted the task progress list.
  6. Tk implements -transparentcolor by setting WS_EX_LAYERED from an idle
     handler, which rewrote the extended window style and silently dropped
     WS_EX_NOACTIVATE. Styling during construction was undone before the first
     frame completed. Now applied after every geometry commit, and only on change.
  7. Display enumeration ran on EVERY frame, because the frame path called
     redock(). Part 5 forbids constant polling. Now cached, refreshed only by the
     rate-limited monitor check; asserted by test.
  8. Backend submission ran on the UI thread (section 9). The most serious of
     these.
  9. Permission denial was rendered as a task ERROR rather than as a permission
     prompt, because the bridge flattened tool status into a status enum and the
     mapper had nothing to distinguish them. Fixed with the three-key allowlist.
 10. Five redaction defects, each found by a test and each a real leak or
     mis-redaction: `Authorization: Bearer <jwt>` redacted the word "Bearer" and
     left the token; GitHub-style ghp_ keys were missed because the pattern
     required a hyphen; "my api key is VALUE" redacted the word "is"; handle
     substitution used the separator capture group and emitted a bare
     "= [handle]"; NaN timestamps passed a positivity check.

Pre-existing, outside this milestone:
 11. tests/test_windows_real.py::test_filtering_by_name_finds_this_interpreter
     enumerated with limit=20 and then asserted the running interpreter was in the
     result. This machine has 22 live python processes, so the current one fell
     outside the truncated result and the test failed - while filtering by name
     demonstrably does find it (probed: limit=20 misses, limit=40 contains). The
     assertion was really about enumeration order. Limit raised to 512. This is a
     minimal robustness fix, not a relaxation: the property named by the test is
     unchanged and was previously untestable under load.

14. SECURITY AUDIT
--------------------------------------------------------------------------------

The companion is an untrusted presentation boundary. It is treated as one.

  - UI text is never treated as an instruction. It becomes a normal Agent request
    through the existing lifecycle and nothing more. Tested.
  - The companion cannot bypass permissions. It has no capability access at all;
    every request goes through the Agent, which goes through the PermissionManager.
    Demonstrated live in real-model run 2, where a confirmation-requiring tool was
    refused.
  - No secrets are stored in UI state. The companion holds task text, a job id, a
    progress list and a terminal message. No credential field exists.
  - Secrets are not rendered from backend events. Redaction is applied to every
    string that becomes a companion event, and raw metadata is never forwarded.
    Tested against api_key, bearer tokens, GitHub keys and labelled/bare handles.
  - Native handles do not escape. The only handle the companion ever touches is
    its own, and it never enters any model or event payload. The handle-key
    redactor strips even mentions from text.
  - Event injection cannot grant permission. Injected or malformed events can at
    worst move the companion's own display state; they cannot reach the Agent, the
    TaskManager or the PermissionManager. Unmappable payloads are dropped.
  - The companion imports no Windows capability and no Agent. Asserted by AST
    inspection of the module's imports, not by matching prose.

--------------------------------------------------------------------------------
15. PERMISSION / CANCELLATION / VERIFICATION AUDIT
--------------------------------------------------------------------------------

  - Exactly one PermissionManager, owned by the product entry point. The companion
    holds a reference to nothing of the sort; it is not importable from the
    companion layer.
  - STOP and Escape both request cancellation through the existing bridge, which
    calls Agent's active cancellation token. No separate cancellation mechanism was
    introduced. Tested that the token is actually requested.
  - The UI reflects CANCELLATION_REQUESTED and then WAITS. The companion does not
    claim "cancelled" until the backend reports task_cancelled. Tested both
    directions, including a task that completes after a cancel request.
  - Verification remains independent and authoritative. The companion renders a
    verification event; it never produces one and never interprets one as success.
  - Terminal status is derived from backend state only. Success is never inferred
    from the absence of errors - the companion stays in THINKING if no terminal
    event arrives rather than rounding up to done. This is deliberate and is a
    known behaviour to be aware of: see limitations.

18. KNOWN LIMITATIONS OF M2.16.UI
--------------------------------------------------------------------------------

1. The companion stays in THINKING if the backend never emits a terminal event.
   This is deliberate - Part 13 forbids inferring success from the absence of
   errors - but it means a backend that dies silently leaves the user looking at
   "Working..." with a working STOP button and no explanation. A future watchdog
   could surface "still waiting" without claiming an outcome.

2. Sleeping is not click-through. See section 6. The two requirements conflict and
   the compromise is documented rather than silently chosen.

3. The process is DPI-virtualised (awareness "unaware"), so companion geometry is
   expressed in the virtualised coordinate space that Tk also uses. It is
   self-consistent and validated on real hardware, but it is not per-monitor DPI
   aware. Fixing that means a process-level manifest change, which is outside this
   milestone's blast radius and was deliberately not done.

4. Multi-monitor placement is validated on a single-monitor machine. The geometry
   is tested exhaustively against synthetic displays including negative virtual
   desktop coordinates, and against the real single display, but no second
   physical monitor was available.

5. The companion has no tray icon, no settings panel and no theming. Deliberate:
   Part 23 asks for a companion, not an application suite.

6. Real-model tool selection for M2.16.6 workflows is unproven (section 12).

1. The full suites print "Windows fatal exception: access violation" repeatedly to

   the exact M2.16.6 baseline (3163 passed / 197 skipped) and still emits ~194 of
   these. M2.16.UI's own suites emit zero. Not investigated further; out of scope
   and not a regression.

2. This machine currently runs 22 python processes, which is what exposed the
   limit-truncation fragility fixed in section 13.11.

3. A stale ApplicationFrameHost from an earlier session (30-09) is present and can

   tests flaked once during a full real run and pass in isolation; the full real
   suite is green.

22. RECOMMENDED NEXT MILESTONE

M2.17 Persistent Autonomy - entered with ONE prerequisite task: make the model

The reasoning is specific. Seven milestones of desktop capability now exist and are

autonomy on top of tools the model does not select would produce a milestone whose
capability is real and whose product surface is empty. Closing the selection gap -
tool descriptions, catalogue exposure, or model choice - is worth more than any new
surface right now.

23. FINAL VERDICT

M2.16.UI is COMPLETE WITH LIMITATIONS.

The companion exists as a real product surface: a borderless, edge-docked
presence that wakes on click, takes a task through the existing Agent, shows
meaningful progress, offers a cancellation that reports itself honestly, displays
the outcome and retracts - and then closes without leaking a window, a thread, a
timer or a subscription. It was validated on real Windows across all four edges at
real DPI, soaked for 32 minutes over 640 cycles, and driven end-to-end by a real
Ollama model through the production permission path.

The architectural constraint that mattered most - that the companion is a client
and not a second control plane - held throughout, and is enforced by tests rather
than by convention. Five redaction defects, six state-machine and lifecycle
defects, a DPI/extended-style interaction, a per-frame display enumeration and one
serious UI-thread blocking bug were found by validation and fixed.

The honest headline is the real-model result: the companion integrates correctly
with the model, and the model does not yet use the desktop workflow tools. That
gap is stated rather than smoothed over, and it is what should be worked next.
